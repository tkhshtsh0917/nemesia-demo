# ローカルの性能と順位付けの評価

[English](../performance.md)

## 応答時間とサイズ

Nemesia 0.1.0、Rust 1.99.1、wasm-bindgen 0.2.129、Node 24.22.1、Playwright 1.64.1を使い、Apple M5 ProとmacOS 26.6.2（arm64）で計測しました。合成データは1候補にキー1個、2文字の接頭辞で1,296グループです。配布物を使った再計測の本体は `b7ce07e` です。シードを固定した200クエリで完全接頭辞と曖昧な接頭辞を交互に入力しました。ブラウザはPagesと同じ構成の成果物をlocalhostでヘッドレス実行し、20回のウォームアップ後にクエリ種別ごとに100回計測しました。別の実行でも確認しました。時計の分解能はブラウザごとに異なります。

| エンジンとバージョン  | 10万候補の完全一致WASM p95 | 10万候補の曖昧一致WASM p95 | 10万候補の入力からDOM反映までのp95（完全 / 曖昧） |
| --------------------- | -------------------------: | -------------------------: | ------------------------------------------------: |
| Chromium 156.0.8078.4 |                     0.6 ms |                     4.1 ms |                                    17.4 / 17.4 ms |
| Firefox 157.0         |                       1 ms |                       5 ms |                                          9 / 9 ms |
| WebKit 27.2           |                       1 ms |                       4 ms |                                        18 / 17 ms |

初回と、パス置換済みの配布物での再計測とも、この操作列でクエリの失敗は0件でした。前段の実験にはNode 26.8.1を使いました。再計測の曖昧一致のWorker往復p95は順に4.7、5、4 msです。1万候補では、再計測の準備後の曖昧一致WASM p95は3エンジンとも1 ms以下でした。10万候補では、再計測のページ遷移からWorker準備完了までに99〜199 msを要しました。localhostでの転送、WASM初期化、解析、検証を含みます。モバイルのエミュレーションは機能テストに使いました。計測値はこのデスクトップ環境と合成データでの結果です。

|  候補数 | 素の索引サイズ |  gzipサイズ | ネイティブの索引生成 | NodeのWASMでの索引読み込み |
| ------: | -------------: | ----------: | -------------------: | -------------------------: |
|  10,000 |    1,370,848 B |   324,701 B |               8.7 ms |                     5.7 ms |
| 100,000 |   11,243,056 B | 2,716,095 B |              62.5 ms |                    22.4 ms |

バインディング生成後のWASMは170,562 B、gzipで84,141 Bです。別途OSで測った10万候補のネイティブ索引生成のピークRSSは80.9 MiBでした。ローカルに完全な辞書を置いてデモの7文書をSudachiで抽出した場合は約60 msで、ピークRSSは84.2 MiBでした。RSSはネイティブプロセスの指標です。ブラウザのピークメモリは未計測です。展開後の上限と処理量上限は別途検証しました。

10万候補で、出力の順序が基準と一致することを計測の外で確認し、実行順を交互に変えたネイティブの比較を4回行いました。曖昧一致の1クエリあたりの平均は、事前に正規化した全キーの走査が8.93〜9.18 ms、Trieは0.47〜0.54 msでした。完全一致では、ソート済みキーの範囲を探索する方式が約0.001〜0.003 ms、汎用の順位付けを行うTrieは0.047〜0.062 msでした。ソート済みの方式はキーの配列を別に持ちます。観測したWASMの目標を完全・曖昧一致とも満たしたため、リリースでは索引表現を一つに統一します。

## 順位付けの品質

デモ用に作成した7文書を対象に、重みとは独立に人手で入力と意図を付けた固定の31例で比較しました。SudachiDict Core 20261015で39候補を抽出しました。ビルド時の重みだけを変え、同じ上位8件、変換、照合を使いました。通常入力12件、読み9件、誤入力10件を含みます。

| 重み                 | Recall@8 |  MRR@8 | 1位の正答 |
| -------------------- | -------: | -----: | --------: |
| 文書頻度             |  31 / 31 | 0.9516 |   28 / 31 |
| 文書ごとのBM25の合計 |  31 / 31 | 0.9677 |   29 / 31 |

BM25で通常入力3例が1位に上がり、元は1位だった2例が2位に下がりました。例えば「せか」で「世界史」が上がり、「世」で「世界」が下がりました。読みと誤入力で結果は同じでした。文書頻度を既定のままとし、コーパス設定でBM25も選べるようにします。改善が一般化するか判断するには、独立に意図を付けた、より大きな評価セットが必要です。

## 再現手順

[リリース手順](release.md)でサイトをビルドし、デモリポジトリで次を実行します。

```sh
node tools/bench/performance.ts /path/to/nemesia
node tools/bench/quality.ts /path/to/nemesia /path/to/system.dic
```

`artifacts/bench/` のローカルレポートに、成果物のハッシュ、実行環境、データの識別情報、件数、p50・p95・p99またはクエリごとの順位が出ます。ネイティブのA/B計測は本体リポジトリで `cargo run --locked --release -p nemesia-builder --example bench_compare -- CANDIDATES_JSONL QUERY_LINES` を実行します。`tools/bench/workload.ts` で合成データとクエリ列を再現できます。
