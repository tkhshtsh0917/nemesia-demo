# リリースと検証

[English](../release.md) · [ブラウザ統合](browser.md)

Rustリポジトリは、タグの検証後、ネイティブCLI、WASM、ツールチェーンとABIのメタデータ、Rust APIリファレンスのアーカイブ、チェックサム、ライセンス表記を公開します。デモは実行ごとに公開済みのタグを一つ厳密に選び、各入力成果物のSHA-256が期待値と一致することを確認します。リリースロックにはタグと成果物の期待ハッシュを記録します。リリース起点や手動の配信では、明示的なタグを一度だけ解決し、その固定情報を来歴として記録できます。どの場合も同じ固定情報をネイティブの索引生成、バインディング生成、ブラウザテストに使います。開発時は成果物のローカル入力を明示的に指定することもでき、同じ検証を行います。ビルドでは隣接したチェックアウトを自動探索しません。

デモのワークフローはCLIとプラットフォーム、ABIの互換性、コーパスの来歴、入力ハッシュ、期待出力を検証します。機能とブラウザのテストを実行し、静的なPages成果物を一つ生成します。検証したその成果物を公開します。文書横断の統計はビルドの出力に置きます。Pagesにはデモの成果物とデータの出典表記に加え、同じタグから生成したRust APIリファレンスを `/api/rust/` 以下に配信します。文書アーカイブも展開前にハッシュを照合します。選択したリリース、デモのコミット、データのハッシュを配信の来歴として保存します。

検証ワークフローを共有し、配信の入口を二つ用意します。

1. リリースの公開後、信頼する通知が渡したタグの検証を開始します。配信直前にタグが対象となる最新の安定版であることを確認し、本番配信を直列化して、遅れて届いたイベントが新しいPagesを置き換えないようにします。
2. 手動用のワークフローでは、ロールバックに使うものを含め、対応する公開済みタグを明示して選べます。同じ検証を行い、成功時のみ配信します。検証に失敗しても現行のPagesは引き続き利用できます。

検証ジョブの権限は読み取り専用とし、PagesとOIDCの権限は配信ジョブにだけ付与します。URLの配信元を検証し、展開後のバイト上限を適用します。デモのCI単体テストには固定のローカルデータを使い、データセットの都度ダウンロードに依存させません。PlaywrightでChromium、Firefox、WebKitをデスクトップ・モバイルプロファイルにて検証します。IME、キーボード、ポインター、安全な描画、重複排除、古い応答への対処、回復、サブパス配信を確認します。モバイルのエミュレーションではテストホスト上のブラウザの挙動とレイアウトを確認します。[GitHub Pagesのカスタムワークフロー](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)。
